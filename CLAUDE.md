## The one-paragraph version

`venice.primalmoves.com` is a **static site generated by one Python script**.
`tools/build_d9.py` writes every page into `design-9/`. Cloudflare serves
`design-9/` as the site root. There is no framework, no node build, no CMS.
Deploying is a `git push` to `main`; `deploy.command` does that for you.

## The rule that matters most

**Never edit the HTML in `design-9/`.** It is generated. Edit
`tools/build_d9.py` and rebuild:

```bash
python3 tools/build_d9.py
```

Hand edits to `design-9/*/index.html` are silently destroyed on the next build,
and the next build is whenever anyone touches anything.

CSS, `config.js`, `analytics.js` and `admin.js` **are** hand-authored. Edit
those directly — the build does not generate them.

## How a deploy actually works

`wrangler.toml` at the repo root defines a Cloudflare Worker with
`[assets] directory = "./design-9"`. The build command on Cloudflare is:

```
cp -r assets design-9/ && npx wrangler deploy
```

That `cp` is why **`design-9/assets/` is gitignored** — it is a build-time copy
of `assets/`, not something to commit. Anything a page needs to serve must live
under `assets/` or it never reaches the site.

Pushing to `main` is the deploy. Cloudflare builds in about a minute.

### deploy.command

Jeremy double-clicks `deploy.command` in Finder. It:

1. unpacks the newest `pm-*.tar.gz` in the folder, if there is one, then deletes it
2. deletes any paths listed in `pm-remove.txt` (a tarball can add files but never remove one)
3. restores `design-9/schedule.json` and `design-9/events.json` from git
4. commits everything as `site update <date>`
5. `git pull --rebase --autostash`, then pushes

**So: if you want work deployed, hand Jeremy a `pm-*.tar.gz` in the repo folder.
Do not push a branch and expect `deploy.command` to find it** — it only commits
what is in his working tree. A branch on GitHub his Mac has never fetched will
make `deploy.command` correctly report "nothing to deploy", which looks like a
failure and is not one. If you do push directly to `main`, say so plainly, and
tell him to `git pull` before his next `deploy.command`.

### Files the robots own — never commit these by hand

`.github/workflows/refresh-data.yml` runs every four hours and rewrites:

- `design-9/schedule.json` — the timetable, pulled from Mindbody's public
  class-times endpoint by `tools/fetch_schedule.py`
- `design-9/events.json` — pulled from Luma's public ICS feed

They are committed straight to `main` by `github-actions[bot]`. Committing your
own copy causes a rebase conflict during `deploy.command`. The script has a
special case for exactly these two files; do not give it more work.

`.github/workflows/index-photos.yml` does the same for `design-9/photos.json`.

## The EDIT panel — what is actually true

**The panel is invisible to visitors. There is nothing to flip before launch.**

This is the single thing most likely to be got wrong, because two comments in
the repo still say otherwise. The truth, in the code:

1. Every real page carries a loader gate — 19 of the 22 HTML files; the other
   three are instant `location.replace` redirect stubs with no chrome at all.
   `admin.js` is not even *fetched* unless the browser has already logged in:

   ```js
   if (localStorage.getItem("pm_admin") !== "1") return;   // no fetch at all
   ```

2. `admin.js` independently fails closed on the same check, at the top of the
   file, **before** `studioOpenToAll` is ever read.

So `studioOpenToAll: true` in `config.js` is unreachable. It is dead config.
Staff reach the panel by going to `/admin/`, entering the passphrase, and
getting `pm_admin` set. Writes additionally need the worker's write key.

## The other Worker

`tools/wrangler.toml` is a **different** Worker — `pm-studio`, the photo store
(KV `PM_STUDIO` + R2 `pm-photos`). Deploy it with
`npx wrangler deploy -c tools/wrangler.toml`. It has nothing to do with serving
the site. Two configs, two Workers, on purpose.

## Known traps

- **Running git through the Cowork device bridge leaves `.git/index.lock`
  behind** — the bridge blocks git's own cleanup `rm`. It will block Jeremy's
  next commit. Delete it when you see it.
- **The heading system infers styling from markup shape.** A container holding
  a `.kicker` and a heading gets a transform applied whether or not it wanted
  one, enforced with `!important`. It has already broken the legal pages once
  and hidden section headings from screen readers once. See `HANDOFF.md` for
  the measurement and the planned fix. Until then: a page that is a document,
  not a marketing section, must not put a `.kicker` and a heading in the same
  container.
- **Two addresses.** `hellovenice@primalmoves.com` for everything;
  `events@primalmoves.com` for hosting and private hire only.
- **Booking links live in `config.js`**, resolved from Mindbody pricing-option
  and contract ids. `analytics.js` reads them back to classify booking events —
  repoint a link there and the analytics follow on the same deploy.

## Before you say it works

This project has a house style of measuring rather than asserting. Some of it
is scripted, most of it is not — but the expectation is that a claim about the
site is backed by something you ran:

- rebuild and diff, don't assume the build is clean
- `node --check` the JS files you touched
- render the pages in a browser at 390px and 1280px and compare element boxes
  before and after — layout regressions here are usually CSS specificity ties,
  not obvious breakage
- axe-core is clean across every page at both widths. Keep it that way.
- the live site blocks some sandboxes as a bot. A `000` or a Cloudflare 1010
  means your network was refused, **not** that the site is down. Check from
  somewhere else before reporting an outage.
